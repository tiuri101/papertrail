# Contributing to Papertrail

Thanks for your interest in improving Papertrail! Bug reports, feature ideas, documentation fixes, and pull requests are all welcome.

## Reporting issues

- **Bugs, feature requests, and PDF retrieval problems:** open an issue using one of the forms.
- **Questions and setup help:** use [Discussions](https://github.com/tiuri101/papertrail/discussions).
- **Security vulnerabilities:** never open a public issue; follow [SECURITY.md](SECURITY.md).

Please don't paste passwords, tokens, session cookies, or unpublished review data into issues or pull requests.

## Development setup

Only PostgreSQL runs in Docker; the API, workers, and frontend run on your machine. The [local development guide](docs/local-development.md) covers setup on Windows, macOS, and Linux. In short (Windows PowerShell):

```powershell
Copy-Item .env.development.example .env.development
.\scripts\dev.ps1 setup
.\scripts\dev.ps1 create-admin
.\scripts\dev.ps1 start
```

Read the [developer guide](docs/developer-guide.md) and [architecture overview](docs/architecture.md) before larger changes.

## Branches and pull requests

- Base your work on **`dev`** and open pull requests against `dev`. `main` only receives merges from `dev`, and every merge to `main` publishes a release.
- Keep each pull request focused on one change, and fill in the pull request template.
- Discuss larger features in an issue first, so the design can be agreed before you invest the time.

## Before you open a pull request

Run the checks for every part you changed:

```powershell
.\scripts\dev.ps1 test        # backend tests + lint, frontend typecheck/lint/tests

cd backend; python -m mypy app
cd frontend; npm run verify   # includes the Playwright browser tests
cd browser-extension; npm run typecheck; npm run lint; npm test
```

Continuous integration runs the same checks on every pull request.

## Design rules

The full list is in the [developer guide](docs/developer-guide.md#design-rules). The ones reviewers check most:

- Add a failing test before fixing a defect or adding non-trivial domain behavior.
- Keep FastAPI routes thin; business rules belong in domain services, and FastAPI re-validates everything the UI enforces.
- Every persistent schema change needs an Alembic migration, and an autogenerated migration must be reviewed before committing.
- Write audit events in the same transaction as the action they describe, and never overwrite imported records or individual reviewer decisions.
- Never start long-running work from a request thread; enqueue a background job instead.
- LLM output only ever suggests. Reviewer decisions stay authoritative.
